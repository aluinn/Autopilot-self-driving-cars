# Contributing to Autopilot

Thanks for your interest! Autopilot is a small, readable teaching project, so the bar for
contributions is: keep it simple, keep it dependency-free at runtime, and keep the code
friendly to someone reading it for the first time.

By taking part you agree to follow the [Code of Conduct](CODE_OF_CONDUCT.md).

## Finding something to work on

- Browse the [issue drafts](docs/issues) (copy one into a new issue) or the open issues labelled **good first issue**.
- Have a bigger idea? Open a feature request first so we can agree on the shape before you write code.

## Setup

You need **Node.js 20 or newer** (for the tests and tools). The app itself needs no install.

```bash
git clone https://github.com/<your-username>/Autopilot-self-driving-cars.git
cd Autopilot-self-driving-cars
npm install            # only dev dependency: Playwright (screenshots, e2e)
npm start              # serves the app at http://localhost:8000
```

## Commands

| Command | What it does |
|---|---|
| `npm start` | Serve the app on port 8000 (`node tools/serve.js [port]`) |
| `npm run lint` | Syntax check, whitespace rules and `index.html` file references |
| `npm test` | Unit tests (Node's built-in test runner) |
| `npx playwright install chromium` | One-off: download the browser used by the e2e test |
| `npm run e2e` | End-to-end smoke test in a real browser |
| `npm run bench` | Simulation benchmark (see [docs/PERFORMANCE.md](docs/PERFORMANCE.md)) |
| `npm run train-demo` | Re-train the demo brain and rewrite `demo.js` |
| `npm run screenshots` | Regenerate the README screenshots in `docs/assets/` |

There is no build step and no type checker: the project is plain browser JavaScript with
global scripts loaded in order from `index.html`. `npm run lint` is a lightweight stand-in.
If you would like to propose adding ESLint or JSDoc type-checking, please open an issue first.

## Making a change

1. Fork the repo and create a branch from `main`: `type/short-description`, for example
   `feat/pause-button`, `fix/narrator-demo-text`, `docs/faq-typo`.
2. Match the existing style: small files, plain language comments that explain *why*, no frameworks.
   Don't reformat code you aren't changing.
3. Add or update tests when you change logic in `network.js`, `car.js`, `track.js`, `evolution.js`
   or `utils.js`. UI changes: describe how you checked them, and add a screenshot to the PR.
4. Run `npm run lint && npm test && npm run e2e` before pushing.
5. Add a line under **Unreleased** in [CHANGELOG.md](CHANGELOG.md) for anything a user would notice.

### Commit messages

We use [Conventional Commits](https://www.conventionalcommits.org/): `type(optional scope): summary`.

Types: `feat`, `fix`, `docs`, `test`, `refactor`, `perf`, `chore`, `ci`.
Examples: `feat: add pause button`, `fix(narrator): handle trained brains at generation 1`.

### Pull request rules

- One logical change per PR; keep it small enough to review in one sitting.
- Fill in the PR template and link the issue (`Closes #123`).
- CI (lint, unit tests, e2e, CodeQL) must be green.
- Be open to feedback. Reviews are about the code, not about you.

### Regenerating the demo brain

`demo.js` is generated by `npm run train-demo`; don't edit it by hand. If you change the network
shape, car physics or sensor layout, re-train it and mention that in your PR. Training runs
80 generations and takes a little while.

## Reporting bugs and security issues

Use the bug report form. For security problems, follow [SECURITY.md](SECURITY.md) and do not open a public issue.
